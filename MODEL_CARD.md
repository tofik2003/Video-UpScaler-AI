# Model card — `espcn_x2.tflite`

PLAN.md §9 requires provenance to be recorded for every bundled model. This is that record.

## Status: **development artifact, not shippable**

| | |
|---|---|
| Architecture | ESPCN sub-pixel CNN (Shi et al. 2016): conv 5×5/64 → conv 3×3/32 → conv 3×3/12 → depth-to-space(2) |
| Scale | 2× integer only |
| Input | `[1, 360, 640, 3]` float32, RGB, 0..1, NHWC |
| Output | `[1, 720, 1280, 3]` float32 |
| Weights | float16 (`supported_types = [tf.float16]`) |
| Size | ~56 KB |
| Trained on | **Synthetic images** — gradients, rectangles, angled stripes, checkerboards, discs, plus 1% Gaussian noise |
| Training run | 120 epochs × 60 steps = 7,200 steps, batch 24, patch 72, Adam 2e-3, final MAE loss 0.0233 |
| Licence | Code: this repo. Weights: generated by `models/espcn/espcn.py`, no third-party data involved |

## What this model is for

It exists to make the Phase 2 integration **testable**. With it in `assets/` the whole path can be
exercised end to end — LiteRT load, GPU delegate negotiation, the `glReadPixels` round trip, the
two-copy upload — which is the part of Phase 2 that has nothing to do with model quality and
everything to do with whether the pipeline works.

It also makes the Phase 0 latency gate measurable, since a benchmark needs a real model to run.

## What this model is not

**It was not trained on real imagery.** Synthetic training data has no natural texture statistics,
so the learned sub-pixel filters are tuned to stripes and edges rather than to skin, foliage, or
compression artefacts. Do not judge Tier 2 quality by this model, and do not ship it.

## Producing a shippable model

```bash
pip install -r tools/requirements.txt
python3 models/espcn/espcn.py train --data /path/to/images --epochs 300 --steps-per-epoch 200
python3 models/espcn/espcn.py eval  --model models/espcn/espcn_x2.tflite
```

**Check dataset licensing first** (PLAN.md §9). DIV2K and Flickr2K licensing must be verified per
use. Training on your own or clearly licensed footage removes the question entirely and produces a
model tuned to phone video rather than to DIV2K crops.

The gate in `eval` is that ESPCN must beat the bicubic reference on **both** PSNR and SSIM. Update
this card with the training set, step count, and measured numbers before the model ships.

## Measured — and why the gate still fails

Host-side evaluation (`models/espcn/espcn.py eval`), synthetic test set, native 360×640 input:

```
espcn                  PSNR  35.01 dB   SSIM 0.9169
  reference (bicubic)  PSNR  40.12 dB   SSIM 0.9208
  delta                PSNR  -5.11 dB   SSIM -0.0039   -> FAIL
```

Host CPU latency at 360×640: **~154 ms median** on x86 with XNNPACK. That is *not* the Phase 0
number — the gate is ≤20 ms on a mid-range phone GPU, measured inside the effect chain.

**The gate fails, and the reason matters.** More training moved the model from 26.97 dB to 35.01 dB,
so training, conversion, and the runtime are all demonstrably working. What it cannot beat is
bicubic *on this test set*. The synthetic content is piecewise-smooth — flat rectangles, linear
gradients, regular stripes — which is close to bicubic's best case, so there is almost no headroom
for any learned model to exploit. Real photographic content is where bicubic makes large errors and
sub-pixel CNNs win by several dB.

So: the plumbing is proven, the gate is **unproven**, and the honest statement is that Tier 2
quality has not been established. Re-run `eval` against real imagery before claiming otherwise. Do
not treat the 35.01 dB as a quality result.

## Known constraints

- **Landscape only.** The input is 640×360. Portrait sources cannot be fed to these weights without
  a rotation stage or a second set. `UpscaleChain.isSupported()` refuses rather than distorting.
- **Fixed input shape.** Dynamic shapes were rejected deliberately: the GPU delegate performs worse
  on them, and a static shape is what the Phase 0 benchmark specifies.
- **No INT8 quantization.** Sub-pixel convolutions are sensitive to it and the loss is visible on
  gradients. FP16 halves the size versus FP32 with no visible cost.
